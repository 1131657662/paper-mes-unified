# 测试环境自动部署

`Frontend quality` 在 `main` 成功完成后，由 `Deploy MES test` 自动部署到
`https://mes-test.nbsmzwl.cn`。该 workflow 只允许使用 `workflow_run.head_sha`，并且同时检查
来源分支、仓库和质量检查结论；生产服务、生产路径和生产 secrets 不在流程中出现。

GitHub 仓库的 `mes-test` Environment 需要配置以下四个 secrets：

| Secret | 用途 |
| --- | --- |
| `MES_TEST_SSH_HOST` | 测试服务器地址 |
| `MES_TEST_SSH_USER` | 测试专用部署账号 |
| `MES_TEST_SSH_PRIVATE_KEY` | 测试专用 SSH 私钥 |
| `MES_TEST_SSH_KNOWN_HOSTS` | 固定的服务器主机指纹 |

部署账号只能通过 `sudo -n /usr/local/sbin/paper-mes-test-deploy <sha>` 执行固定脚本，不能执行任意 root 命令。服务器上的 wrapper 会从待部署 commit 读取版本化部署脚本，避免服务器脚本与仓库代码漂移。

部署顺序如下：

1. 校验测试源码工作树干净，并确认 `origin/main` 等于 CI 成功的 commit。
2. 备份测试 Jar 和环境文件。
3. 生成统一发布元数据，构建前端和后端，并原子更新测试环境的
   `PAPER_MES_BACKEND_VERSION`、`PAPER_MES_FRONTEND_VERSION`、`PAPER_MES_GIT_SHA`
   和 `PAPER_MES_BUILD_TIME`。
4. 仅重启 `paper-mes-test.service`，轮询本机健康检查直到 `UP`。
5. 发布带 SHA 的前端版本，保留现有版本化发布目录。
6. 在 Actions runner 上检查首页 `200`、未登录鉴权 `401` 和公网 actuator `404`。

缺少任一 secret、源码存在未提交改动、CI SHA 不一致或健康检查失败时，流程立即失败并停止，不会自动触碰生产环境。
