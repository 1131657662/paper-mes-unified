# 卷纸加工 MES 范围确认与上线前深度分析

日期：2026-08-01

## 1. 最终范围确认

系统仅面向 PC 浏览器，业务闭环为：建档 -> 加工单与工艺 -> 原纸/成品卷 -> 加工回录 -> 仓库级库存 -> 出库 -> 结算收款 -> 追溯 -> PC 报表与导出。仓库只保留仓库这一业务维度，不建设库区、库位、货架、容量或按库位调拨。

以下范围明确不新增菜单、路由、API、权限、表或定时任务：精细库位；PDA、条码/二维码和扫码枪；移动端适配；班组、排班、停机、工时、OEE、设备联网；发票开具、税控、财务软件、总账和凭证；信用额度、授信审批、逾期拦截和催收流程。

已确认保留：发票/税率等结算元数据及独立入口；结算收款和账龄/收款进度报表；独立催收提醒入口；现有报表订阅。上述功能不能向税控、信用或自动催收扩展。

## 2. 已确认事实与新发现

### 2.1 迁移与 schema

1. 初始审查发现基线曾缺少部分已发布迁移结构。当前 `sql/01_schema_v4.1.sql` 含 62 张表，`sql/schema-baseline.version` 为 `3.53`，已纳入 `biz_settle_detail.active_order_uuid`/活动唯一键、`idx_finish_unassigned_order`、`rpt_report_query_snapshot`、不可变成品库存账本、下发版本审计及幂等约束、token 摘要列和已版本化性能索引；迁移目录当前有 72 个 `V*.sql`。这些结构必须持续由 schema-diff 门禁验证，不能仅凭文件编辑认定一致。
2. `src/main/resources/application-prod.example.yml` 禁用 `app.schema-bootstrap`。生产只能依赖迁移。
3. 初始生产冒烟曾只执行基线后登记历史。当前 `deploy/test-production-profile-startup.ps1` 已在隔离库执行基线后的 pending SQL，并写入 `running/failed/applied` 状态；不再调用 `Register-MigrationBaseline`。默认 pending window 是 `3.49 -> 3.53`，其余窗口须显式传入基线版本。
4. 当前 `deploy/apply-paper-mes-migrations.example.sh` 已加入命名锁、checksum 不一致拒绝、`running/failed/applied` 状态和失败后显式 `MIGRATION_RETRY_FAILED=1` 重试开关；baseline 登记必须传版本和 canonical schema checksum。`deploy/check-paper-mes-schema-diff.example.sh` 还会断言每个基线后的脚本确实以 `applied|applied` 执行，不能退化为 fabricated baseline。
5. `sql/02_index_p3-3.sql` 的性能索引已由 `V3.51__version_p3_indexes.sql` 纳入版本迁移；旧文件只保留历史兼容，不得作为发布入口。
6. 在临时库用历史 `01_schema_v4.1.sql` 逐个重放全部 `V*.sql`，会在 `V1.6__add_order_settlement_snapshot.sql` 等升级脚本因已存在列/索引而失败。结论未变：尚无可直接重放 V1-V3.49 的统一历史前置 fixture，不能把“基线 + 登记全部版本”称为完整迁移验证。当前已真实验证 canonical baseline + `3.49 -> 3.53` pending window；V1-V3.49 全链仍须等经业务确认的历史 fixture，报告中必须持续标为未验证。
7. 2026-08-02 已用本机及发布环境 MySQL 执行 `deploy/verify-schema-diff.ps1 -BaselineVersion 3.49`：实际重放 `V3.50__hash_session_tokens.sql`、`V3.51__version_p3_indexes.sql`、`V3.52__add_inventory_transaction_ledger.sql` 与 `V3.53__add_process_order_issue_versions.sql` 后 schema signature 一致。Shell 门禁已通过 `bash -n` 与迁移契约测试；该结果不替代 V1 至 V3.49 历史 fixture 验证。

阶段 0 将把当前 `01_schema_v4.1.sql` 定义为可发布的 canonical baseline（版本记录在 `sql/schema-baseline.version`），对基线之前的旧升级脚本只做契约/存量兼容审计；冒烟和 schema gate 明确重放“上一个发布基线到当前版本”的 pending window，并在没有真实历史 fixture 时显式报告“未验证 V1-V3.49 全链”，不得静默宣称全链通过。后续若要验证旧库逐版升级，必须另行提供经业务确认的历史 fixture。

### 2.2 核心业务闭环

主链路的表和服务已覆盖加工单、原纸、工序、成品、出库、结算、收款和报表，但当前闭环仍有以下断点：

- 加工单通用 `PUT /status` 已固定返回 405，回退改为受 `order:manage`、目标状态和原因约束的 `PUT /rollback`；成品卷通用 `PUT /status` 也已关闭。仍有 `PUT /rolls/{rollUuid}/status` 原纸状态入口，且没有原因/审计语义，阶段 1 必须关闭或替换为明确业务命令。
- `FinishRollServiceImpl.changeFinishStatus` 内部仍允许待入库成品转报废；虽然通用 HTTP 路由已关闭，但独立的成品报废命令尚未实现，仍缺专用权限、原因、出库占用校验、审计和库存流水。
- 加工完成可从加工中直接转待回录，未校验物理打印成功；可能形成“未打印但已完成”。
- 普通工序新增/修改/删除没有识别链式阶段及其输出/输入关系，可能留下孤儿阶段和不一致快照。
- 路由 DTO 只校验 `stageLevel >= 1`，未校验连续、唯一、拓扑顺序及所有正数边界；写入时按阶段号匹配可能重复绑定。
- 多母卷消费逻辑按成品删除全部 `FinishOriginalRel`，合并复卷后的其他来源血缘可能被误删。
- 下发后仍可新增计划成品或追加链式工艺，而打印快照不更新，计划、下发单和回录会矛盾。
- 取消出库保留历史明细，但加工单回退 guard 仍把已取消明细当作活动阻塞。

这些问题均属于阶段 1 的上线阻断项；阶段 0 只先建立能阻断迁移/安全回归的门禁。

### 2.3 数据模型与完整性

- 加工单、原纸、成品、成品-原纸关系、出库、结算和收款大量只有 UUID 字段，缺少数据库 FK；需要先做孤儿/跨单数据盘点，再分批加 `RESTRICT` FK 或等效巡检。
- `biz_finish_original_rel` 没有活动 `(finish_uuid, original_uuid)` 唯一约束；多源追溯汇总可能重复。
- 当前库存是 `biz_finish_roll.remaining_weight/finish_status` 与出库锁字段的可变投影，没有不可变库存流水，无法回答任意时点余额和变化原因。
- `BaseEntity` 逻辑删除与 `(business_key,is_deleted)` 唯一键会造成二次删除冲突，已知 `biz_process_config_draft`、系统字典/配置存在风险。
- 重量、件数、金额和状态组合的数据库 CHECK 不完整，不能只依赖服务层。

库存切换采用“切换日开账”：切换时锁定业务写入窗口，按当时核对的成品卷当前余额生成一条 `OPENING_BALANCE` 流水；开账总额必须与旧库存投影逐卷对账并输出差异清单。切换日前不承诺历史时点库存精确重建，绝不从旧快照伪造流水；切换日后库存报表只认流水账本。

### 2.4 权限、审计与安全

- 控制器普遍有 `@RequirePermission`，但原纸/成品通用状态接口的业务规则不足，不能把前端隐藏视为授权。
- 计划变更按确认方案由具备 `order:manage` 的操作者填写原因后提交；必须保存前后内容、原因、操作者、时间、版本号、重新下发记录和旧打印快照，不需要双人审批。
- 成品报废保留独立命令：专用权限、原因、当前库存状态和出库占用校验、审计、库存流水；禁止通用状态接口完成报废。
- 追溯 API/导出只向具备现有结算读取权限的角色返回结算金额、已收、未收和收款日期；仓库、生产/操作角色只能看到卷号血缘、工艺、重量、库存、出库和异常。前端隐藏不是安全边界。
- `AuthServiceImpl` 已改为仅向客户端返回原始 token，数据库查询与存储均使用 SHA-256 摘要；`V3.50__hash_session_tokens.sql` 迁移旧 token，并把列约束为 64 位摘要。仍需在真实升级库验证切换及回退演练。
- `GlobalExceptionHandler.handleOther` 已改为 HTTP 500；校验、重复键、数据库完整性、参数和方法不支持处理器仍须由阶段 0 契约测试持续覆盖 4xx/409/405，避免以后回退到 HTTP 200 业务体。
- 生产示例配置没有仓库密码，但必须持续阻止敏感配置进入日志、导出和配置接口；开发密码仅存在被 `.gitignore` 忽略的本地文件。

## 4. 阶段 0 上线阻断门禁与缺失测试

以下任一项失败均阻断上线：

1. 临时库 canonical baseline 与已执行 pending window 的 `information_schema` 差异非零，或基线缺少现行代码必需表/列/索引。没有可信历史 fixture 时不得将 V1-V3.49 标为“已全链验证”。
2. 迁移并发未互斥、失败后仍登记 `applied`、checksum 可被静默改写，或无法给出备份/恢复/回滚步骤。
3. 生产冒烟只跑基线或将未执行迁移全部登记为 baseline。
4. session token 仍以原文落库/日志输出，或追溯/导出金额未在后端按权限脱敏。
5. 4xx/409/405/500 错误仍以 HTTP 200 返回，或配置/健康端点泄露敏感值。

阶段 0 必补：迁移脚本静态契约、基线/全量 schema diff、迁移锁和失败恢复集成测试；token 摘要/查询/注销测试；全局异常处理器 HTTP 状态测试；生产冒烟完整迁移测试；配置脱敏和 `/actuator/env` 404 测试。阶段 1-5 另需补链式工艺、计划版本、报废、开账对账、血缘、金额权限、R1-R5 指标和三种 PC 宽度 E2E，不能用阶段 0 的绿色替代。

## 5. 实施决定

唯一会阻断“V1-V3.49 全链迁移已验证”这一 P0 验收结论的问题是：仓库没有可确认的 V1.1 前置 schema/匿名历史库 fixture。Git 取证显示最初提交同时加入 schema 与 V1.2-V1.7；该 schema 缺少 V1.2-V1.5 的结果，却已包含 V1.6 的结算快照字段和 V1.7 的用户/会话表，是无法登记为单一版本的混合态，不能安全地反向臆造。默认先采用 canonical `3.53` + `3.49 -> 3.53` pending-window 门禁，并明确把旧全链标为未验证；要清除此 P0 残余，需要业务方提供可脱敏的历史库副本或确认的历史 schema fixture。阶段 0 另以开账前将 `remainingWeight` 视为可用重量、活跃出库 `outWeight` 视为预占重量为默认口径，若业务确认不同则切换前阻断。采用以下默认值：

- 计划变更由具备 `order:manage` 的单一操作者提交原因并立即生成新版本、重新下发；不做双人审批。
- 成品报废保留独立受控命令，可在入库后执行；必须校验占用、专用权限、原因、审计和库存流水。
- 库存只从切换日开账，不回补切换日前历史流水；历史时点报表标明“不承诺精确重建”。
- 账龄桶为 `0-30 / 31-60 / 61-90 / 90+`；驾驶舱默认“本月累计 + 上月同期对比（环比）”，同比仅作为后续可选筛选。
- 发票/税率和独立催收提醒保留但不扩展；追溯金额仅结算读取角色可见，导出采用同一策略。

阶段 0 已按上述边界实现门禁和安全基础；实际验证结果见第 6 节，阶段 1 尚未开始。
